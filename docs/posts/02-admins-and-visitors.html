Admins, visitors and a welcome sign we didn't build (yet)

Craig wanted to try out interactivity, starting with something small: a branded welcome sign in our space with one thing visitors can click. Before touching anything, we read the live API spec and took a read-only look at the space.

What admins control

A Frame has an owner, admins, members and guests. Admins handle settings, analytics, environments and user permissions, and they decide how much visitors can do. The API shows this as a row of *PermissionLevel fields: edit, interact, view, mic, camera, streaming, moderation and more. Each one is set to guest, user, member or admin. The full breakdown is in the roles matrix. We changed none of them.

Why the welcome sign is on hold

The create-asset endpoint doesn't take a body. The spec says to make an asset in the web UI first, read its JSON back through the API, and use that as a template. There's also no endpoint for listing assets, so the API can't show what's already standing at the entry point. We could have dropped a sign at a default position and hoped, but we chose not to guess. The plan and undo steps are written down. The next move needs someone in the browser.

Update: the browser test

Next we tried joining the space as a guest from our agent's cloud browser. The 3D view didn't start. The cloud machine has no GPU, so Chrome falls back to software WebGL, and Chrome's logs show the 3D context being rejected because it would be software-rendered (fail_if_major_perf_caveat + software gl). Frame showed "device could not initialize rendering context" and dropped back to its 2D view. That's a limit of a GPU-less machine, not a fault in Frame. Visual checks need a computer with a real graphics card. Nothing was created or changed in the space.

Update 2: signed in, still no 3D

Once Craig's email was verified, sign-in worked. The 3D scene still won't draw on our GPU-less cloud browser, but Frame's flat mode kept the menus usable: Settings (Permissions, Environment, Branding, Action Editor, Clone, Roles) and the Assets list. That gave us asset IDs. With one ID, a read-only API call showed us what a Text Area is made of: text, font, size, alignment, position, rotation, scale, and the scene it belongs to. Text Areas have no link field, so a clickable welcome sign will need a different asset type, or a text sign paired with a separate link or poll. We still haven't created anything, because we can't yet see where the entry point is. You can now check an asset's field names, without its values, using examples/asset-shape.sh.

Takeaway

The Frame API is good for automating things you've already designed in the UI: settings, access lists, scene switches and copies of existing assets. It doesn't yet let you design a scene from scratch through code.
